The problem and the goal

🧩

Problem

Show how Linux software acquires and analyses meter events, without owning any meter hardware.

🎓

Motivation

Learn how a user-space app talks to a kernel driver, and practise C++ system programming with repeatable input.

🎯

Goal

A virtual smart meter: simulated pulses go through a Linux driver into a C++ app that shows energy, power and cost.

A meter constant maps pulses to energy: 1,000 pulses = 1 kWh. Counting pulses and timing them gives consumption and power.

What I built

🐧

Kernel module (C)

Registers the virtual device /dev/smart_meter and keeps a 64-bit pulse counter.

🔗

IOCTL interface

Three commands: inject pulses, get count, reset. Shared header used by driver and app.

💻

CLI app (C++17)

Menu to simulate pulses, view analytics, reset and exit, with input validation.

📊

Analytics engine

Computes energy in kWh, average power in W and estimated cost in INR.

Driver design: three IOCTL commands

CommandDirectionWhat it does
INJECT_PULSESuser → kernel, u32Adds pulses. Rejects 0 (-EINVAL) and counter overflow (-EOVERFLOW).
GET_COUNTkernel → user, u64Returns the cumulative pulse count.
RESET_COUNTno dataSets the count to zero for a fresh demo.
🔒

Thread safety

A kernel mutex guards every read and write of the shared counter.

🧷

Safe boundaries

Wrong magic number gives -ENOTTY; failed user copies give -EFAULT.

🚪

Misc device

Dynamic minor number, mode 0660, cleanly deregistered on unload.

Analytics formulas

⚡

Energy

kWh = pulses / 1000

🔥

Average power

W = Δ kWh × 3,600,000 / seconds

💰

Estimated cost

INR = kWh × 8

Power uses the time between two readings, so the first reading only stores a baseline. Guards return 0 for a zero meter constant, zero elapsed time, a falling count or negative energy. Values are estimates, not billing.

How data flows

1 · Input

User enters a pulse amount.

2 · Open

App opens /dev/smart_meter.

3 · IOCTL

App asks the driver to add pulses.

4 · Update

Driver validates and updates under a mutex.

5 · Read

App requests the cumulative count.

6 · Analyse

Engine shows kWh, W and INR.

The kernel driver is plain C. The C++ side wraps the device in a RAII class, SmartMeterDevice, so the file descriptor always closes.

Challenges and how I solved them

🔧

Kernel API difference

no_llseek was missing in the installed headers. I removed that entry and the module compiled.

🧱

Header guard bug

The C++ device header lacked its opening #ifndef. Added it to match the #define and #endif.

📢

Build noise

Compiler-name, pahole and BTF messages appeared but were non-fatal, since BTF is skipped without vmlinux.

Limitations and future scope

Honest limitations

  • Pulses are simulated; no physical meter.
  • Count is lost when the module unloads or Linux restarts.
  • Meter constant and tariff are fixed.
  • Needs sudo to open the root-owned device.
